# Функционал и постановка задач

Описание функционала нового медицинского портала и постановка задач (бэклог) по эпикам для выбранной архитектуры **вариант C** ([architecture.md](architecture.md)): NestJS-сервисы, RabbitMQ, CQRS, Keycloak, FSD ([fsd.md](fsd.md)).

Формат задачи: **что делаем** → **чек-лист подзадач** → **критерии приёмки (AC)** → **зависимости** → **оценка** (`S` ≤ 1 день, `M` ≤ 3 дня, `L` ≤ 1 неделя).

> **Эпик R — этапный аудит:** после **каждого** этапа плана ([roadmap.md](roadmap.md)) обязателен проход [Эпика R](#эпик-r--этапный-аудит-поиск-проблем-рефакторинг-и-оптимизация): поиск проблем, рефакторинг по SOLID/KISS/DRY ([fsd.md §7](fsd.md#7-принципы-кода-solid-kiss-dry)) и оптимизация. Этап не считается закрытым, пока аудит не пройден.

## 1. Сущности домена

| Сущность | Владелец данных | Описание |
|---|---|---|
| **Пользователь** | Keycloak / `identity-service` | email, пароль, роли, подтверждение почты |
| **Пациент** | `patient-service` | ФИО, дата рождения, email, дата регистрации, ключи фото/документа |
| **Врач** | `catalog-service` | ФИО, специализация, статус, расписание, фото, **email** (связка с учётной записью, см. [10.2](#102-email-врача-и-приглашение-по-ссылке--m)), `userId` |
| **Специализация** | `catalog-service` | справочник |
| **Расписание врача** | `catalog-service` | период, длительность приёма, рабочие дни (копия — в `scheduling`) |
| **Слот** | `scheduling-service` | дата + start/end, детерминированный ID |
| **Запись** | `scheduling-service` | пациент ↔ врач ↔ слот + статусы `SUBMITTED → APPROVED/DECLINED`, `APPROVED → COMPLETED` (по результату приёма), отмена, **перенос** (смена врача/слота без потери истории — [10.3](#103-перенос-и-изменение-записи-на-приём--l)) |
| **Результат приёма** | `scheduling-service` | заключение и рекомендации к записи: `appointmentId` (unique), текст, автор; вносит врач записи → статус `COMPLETED` |
| **Файл** | `file-service` | объект в MinIO + реестр (владелец, категория, mime, размер, кто загрузил) |
| **Пользователь ↔ врач** | Keycloak / `identity-service` | связка `userId` ↔ `doctorId` (роль `DOCTOR`), по аналогии с пациентом |
| **Событие** | `packages/contracts` | Zod-схема + routing key, версионируется |
| **Проекция отчёта** | `report-service` | посещения: специализация × месяц × количество |

### Статусная машина записи (канон)

Источник истины для переходов и для правил счётчиков отчёта. Меняется только здесь — с синхронизацией каталога событий [architecture §6.4](architecture.md#64-каталог-событий).

| Переход | Кто инициирует | Условие | Событие (outbox) | Эффект на проекцию отчёта |
|---|---|---|---|---|
| создание → `SUBMITTED` | пациент (`USER`) или админ | слот свободен: транзакционный `INSERT` + уникальный индекс `(doctorId, localDate, start)` | `appointment.submitted.v1` | нет |
| `SUBMITTED → APPROVED` | админ | только из `SUBMITTED` | `appointment.approved.v1` | **+1** |
| `SUBMITTED → DECLINED` | админ | только из `SUBMITTED`, с причиной | `appointment.declined.v1` | нет — запись не была учтена |
| `SUBMITTED` / `APPROVED → CANCELLED` | админ (пациент — вне MVP) | нельзя из `DECLINED`, `CANCELLED`, `COMPLETED` | `appointment.cancelled.v1` (+ `previousStatus`) | **−1**, только если был `APPROVED` |
| **перенос**: `SUBMITTED` / `APPROVED` → тот же статус, новый слот/врач | админ (пациент — вне MVP) | только свободный слот (unique-индекс → `409`), новая дата не в прошлом; нельзя из `DECLINED`, `CANCELLED`, `COMPLETED` | `appointment.rescheduled.v1` (старый/новый слот, врач, инициатор) | **нет** — посещение одно, счётчик не трогаем ([10.3](#103-перенос-и-изменение-записи-на-приём--l)) |
| `APPROVED → COMPLETED` | врач записи (`DOCTOR`) | только вместе с внесением результата приёма ([9.2](#92-записи-врача-и-результаты-приёма--l)) | `appointment.completed.v1` | нет — уже учтено при `APPROVED` |

Любой иной переход → **409**; повторная команда (двойной клик) идемпотентна: `200` с текущим состоянием или `409`, без побочных эффектов ([5.4](#54-управление-записями-админ--m), [9.2](#92-записи-врача-и-результаты-приёма--l)). Счётчики проекции считает `report-service` строго по этой таблице ([7.1](#71-проекция-посещений--l)).

## 2. Роли и доступ

| Роль | Keycloak realm role | Доступ |
|---|---|---|
| Администратор | `ADMIN` | `/admin/**`: врачи, пациенты, управление записями, отчёты |
| Пациент | `USER` | `/cabinet/**`: личная карточка, запись, история |
| Врач | `DOCTOR` | `/doctor/**`: свои приёмы, внесение результатов приёма, документы пациентов с приёмом |
| Гость | — | `/auth/**`: вход, регистрация |

Контроль в три уровня: Keycloak (роль в токене) → серверные гарды `web` → guard в `gateway` и в каждом сервисе.

## 3. Модули и сценарии

> Обозначения «модуль 1…7» — функциональные модули системы. Их номера **не совпадают** ни с номерами эпиков (§4), ни с вехами `M1…M6` в [roadmap.md](roadmap.md) — путать их нельзя.

### Модуль 1. Идентичность и доступ (`identity-service`, Keycloak)
- **S1.1** Регистрация: email, пароль, ФИО, дата рождения → **сага**: пользователь в Keycloak → карточка пациента → при сбое компенсация; идемпотентность по email.
- **S1.2** Вход (Auth.js OIDC): access + refresh, сессия в HttpOnly-куках, авто-обновление.
- **S1.3** Выход, завершение сессии на всех устройствах (backchannel logout).
- **S1.4** Восстановление пароля через email.
- **S1.5** Смена ролей администратором → событие `user.role-changed.v1`.
- **S1.6** Защита маршрутов: гость → `/auth/login`; роль не подходит → 403-страница.
- **S1.7** Учётная запись врача: сага «врач ↔ пользователь» (роль `DOCTOR`), идемпотентность по email; смена роли → `user.role-changed.v1`.

### Модуль 2. Справочник врачей (`catalog-service`)
- **S2.1** Список врачей: таблица, поиск по ФИО, пагинация.
- **S2.2** Создание врача с расписанием и (опционально) учётной записью — 9.1; валидация «период кратен длительности приёма» → 400, не 500.
- **S2.3** Редактирование/архивирование без потери истории записей.
- **S2.4** Загрузка фото с кроппером → MinIO через `file-service`.
- **S2.5** CRUD специализаций; удаление занятой специализации запрещено.
- **S2.6** Публикация событий `doctor.*` / `specialization.changed.v1` (пересборка копии расписания в `scheduling`, ISR-revalidate в web).

### Модуль 3. Пациенты и документы (`patient-service`, `file-service`)
- **S3.1** Список пациентов: таблица, поиск, пагинация.
- **S3.2** Карточка пациента: просмотр/редактирование.
- **S3.3** Загрузка фото пациента.
- **S3.4** Загрузка скана: валидация MIME (JPEG/PNG/PDF) и размера (≤ 5 МБ) → понятный отказ.
- **S3.5** Скачивание по presigned-ссылке (TTL 5 мин) с проверкой владельца.
- **S3.6** История приёмов пациента.
- **S3.7** Документы врачом: загрузка в карточку пациента и просмотр/скачивание — только при наличии связи «врач–пациент» (есть приём); у документа — категория и автор загрузки.

### Модуль 4. Расписание и запись (`scheduling-service`)
- **S4.1** Расчёт свободных слотов врача: копия расписания − занятые, без дублей, с учётом таймзоны.
- **S4.2** Слоты по специализации для страницы записи (все активные врачи + окна).
- **S4.3** Бронирование: атомарный INSERT + уникальный индекс слота → 409 при гонке; событие `appointment.submitted.v1` через outbox.
- **S4.4** Управление записями: список с фильтрами, APPROVE/DECLINED/отмена; переходы только из `SUBMITTED`.
- **S4.5** История записей пациента (видна только своя).
- **S4.6** Кабинет врача: список своих приёмов за период (`doctorId` берётся из токена).
- **S4.7** Результат приёма: врач вносит заключение и рекомендации → запись `COMPLETED`, событие `appointment.completed.v1`; пациент видит результат в истории.

### Модуль 5. События, уведомления, аудит
- **S5.1** Outbox в `scheduling`, `catalog`, `patient`, `file`, `identity`: событие пишется в транзакции с данными (продьюсеры — по [architecture §6.4](architecture.md#64-каталог-событий)).
- **S5.2** Outbox-relay: ретраи, метрика лага, отсутствие потерь.
- **S5.3** `notification-service`: шаблоны писем (регистрация, подтверждение записи, approve/decline, отмена, результат приёма, новый документ пациента), очередь + DLQ.
- **S5.4** Идемпотентность потребителей (таблица `inbox`), replay из DLQ.
- **S5.5** (опц.) audit-потребитель: журнал действий.

### Модуль 6. Отчёты (`report-service`, CQRS)
- **S6.1** Проекция `visits(spec, year, month, count)` из `appointment.*`.
- **S6.2** Выбор диапазона дат (max — сегодня), таблица с пагинацией.
- **S6.3** Экспорт CSV.
- **S6.4** Скрипт пересборки проекции (`report:rebuild`) — проекцию можно восстановить из нуля.

### Модуль 7. Платформа и инфраструктура
- **S7.1** Compose-стек: postgres, minio, keycloak, rabbitmq, nginx, mailpit + сервисы; тома и healthcheck'и.
- **S7.2** nginx: TLS, `/` → web, `/api/bff/*` → web (BFF), `/api/*` → gateway, `/media/*` → MinIO, rate-limit, `x-request-id`.
- **S7.3** Keycloak-реалм из манифеста: клиенты, роли, темы писем, service-accounts.
- **S7.4** MinIO-бакеты и политики.
- **S7.5** `packages/contracts`: OpenAPI + Zod-схемы событий + генерация TS-типов.
- **S7.6** CI: lint (границы FSD) → typecheck → тесты с покрытием.
- **S7.7** Prisma: миграции в релизном пайплайне, seed.
- **S7.8** Наблюдаемость: pino + traceId, метрики, `/healthz`, алерты на DLQ/лаг.
- **S7.9** Логирование: Filebeat → Elasticsearch → Kibana — поиск по traceId, дашборды, алерты, ILM-ретеншн.

### 0.2 Качество кода в CI — исключено (SonarQube) — `S`
**Решение: SonarQube удалён из стека** — контейнер, `sonar-project.properties`, scanner и quality gate не используются (ни локально, ни в CI).

Функцию «качество кода как ворота» выполняет существующий пайплайн: **ESLint** (вкл. границы FSD и правила `complexity`/`max-depth`) → **Prettier** → **tsc --noEmit** → тесты с покрытием (`lcov.info` — артефакт PR). Дублирование/complexity/циклы контролируются ревью (fsd.md §9) и [Эпиком R этапного аудита](functional-spec.md#эпик-r--этапный-аудит-поиск-проблем-рефакторинг-и-оптимизация).

### 10.2 Email врача и приглашение по ссылке — `M`
