# Оценки трудозатрат: команда 5 человек и работа с нейросетью

Расчёт по оценкам задач из [functional-spec.md](functional-spec.md) и календарю этапов из [roadmap.md](roadmap.md). Документ — планировочный инструмент: цифры пересчитываются по формулам из §6, когда меняются оценки задач или состав команды.

## 1. Методика

| Параметр | Значение |
|---|---|
| Шкала оценок спеки | `S` ≤ 1 день, `M` ≤ 3 дня, `L` ≤ 1 неделя → **1 / 3 / 5 человеко-дней** |
| Рабочая неделя | 5 рабочих дней |
| Команда | 5 разработчиков, полная неделя = **25 человеко-дней** |
| Источник задач | 66 задач спеки: 57 в этапах 0–5 (вкл. подэтап 2.1 — Эпик 10), 3 вне этапов (1.5, 1.6, 6.4), 6 аудитов Эпика R |
| Критический путь | Цепочка зависимостей внутри этапа (длительность задач `L`/`M` подряд); этапы идут последовательно — между ними ворота Эпика R |

Календарный срок этапа = **максимум** из двух величин:

1. `Σ человеко-дней этапа ÷ 25` — при идеальном параллелизме;
2. `критический путь этапа` — при последовательном проходе цепочки зависимостей.

Далее сроки этапов суммируются (ворота между этапами) и округляются вверх.

**Четыре сценария** (все — на команду 5 человек):

| Сценарий | Описание |
|---|---|
| **A. По спеке** | Нижняя граница: сумма оценок задач без буфера, загрузка 100 % |
| **B. План с буфером ×1.5** | Рекомендуемый сценарий без ИИ: задачи ×1.5 (интеграция, баги, ревью, стенды), аудиты без наценки |
| **C. С нейросетью** | Генерация по промптам/спеке/макетам + ревью человека; коэффициенты §4, буфер ×1.3 на проверку |
| **D. Roadmap** | Календарь плана: 27 недель (этапы 0–5 + подэтап 2.1), консервативный коридор |

## 3. Команда 5 человек

### 3.1 Роли

| Роль | Зона ответственности | Основные этапы |
|---|---|---|
| **Tech-lead / архитектор** (1) | Контракты, `gateway`, `scheduling` (критический путь), решения на арх-ревью, Эпик R | все, доля кода ~50 % |
| **Backend A** (1) | `identity`, `catalog`, саги, события/outbox | 0, 1, 2, 3 |
| **Backend B** (1) | `file`, `patient`, `report`, эксплуатация | 0, 2, 4, 5 |
| **Frontend A** (1) | `web`: оболочка, auth, BFF/SSR, `shared/ui` | 0, 1, 2 |
| **Frontend B** (1) | `web`: таблицы, формы, мастер записи, кабинет врача | 1, 2, 4, 5 |

Реализация — через монорепо и общий пресет: любой разработчик может взять задачу чужой зоны; пересечение зон — на паре «мозговой штурм + ревью tech-lead».

### 3.3 Календарь на команду 5 человек

| Сценарий | Чел-дни (весь проект) | Чел-дни (остаток, этапы 1–5 + 2.1 + пост-MVP) | Недель весь проект | Недель остаток |
|---|---|---|---|---|
| **A. По спеке** (нижняя граница) | 287 | 239 | ≈ 14.5 | ≈ 12 |

| **C. С нейросетью** (§4) | 220 | 200 | ≈ 12 | ≈ 10 |
| **D. Roadmap** (консервативный план) | — | — | 27 | 24 |

Как читать таблицу:

- **A** — достижим только при отсутствии интеграционных проблем и багов; для планирования не использовать.
- **B** — рабочий коридор без ИИ: **17–18 недель остатка** при команде 5. Согласуется с roadmap (24 недели) с запасом ~25 % на непредвиденное.
- **C** — потенциал при системной работе с нейросетью: **≈ 10 недель остатка** (см. оговорки §4.3).
- **D** — roadmap закладывает ёмкость 27 недель × 25 чел-дней = **675 чел-дней**, из них на задачи спеки (287) — **43 %**; остальное — интеграция, баги, аудиты, согласования, внедрение. Это подтверждение того, что оценки спеки — заниженная нижняя граница, и буфер ×1.5 (сценарий B) оправдан.

**Остаток с учётом текущего статуса:** Этап 0 по коду выполнен (см. [roadmap §Статус](roadmap.md#статус-по-факту-кода-mp-v2)) — 34 чел-дни уже израсходованы. Планировать нужно по колонке «остаток».

## 4. Оценка при работе с нейросетью

### 4.1 Что уже готово для ИИ-разработки

Эффективность модели определяется качеством входного контекста — в проекте он собран:

- [prompts-stage1.md](prompts-stage1.md) — готовые промпты на задачи Этапа 1 (P0-контекст + 20 промптов);
- [functional-spec.md](functional-spec.md) — у каждой задачи чек-лист и **проверяемые AC** (главный инструмент валидации генерации);
- [design/*.md](design/README.md) — ASCII-макеты с компонентами MUI и состояниями (вход для фронтенд-генерации);
- [fsd.md](fsd.md) — жёсткие границы слоёв + ESLint-линт (механический отсев нарушений генерации);
- `packages/contracts` + `tsc --noEmit` + CI quality gate — контракты и типы ловят галлюцинации API.

### 4.2 Выигрыш по типам задач

Коэффициент — доля трудозатрат, **остающихся** после применения нейросети (1.0 = без выигрыша).

| Тип задач | Примеры | Коэффициент | Почему именно столько |
|---|---|---|---|
| Boilerplate, каркасы, CRUD, шаблоны | 0.7, 0.8, 3.1, 3.3, 4.1 | **0.35–0.5** | Генерация по спеке + контракту; проверка — линт/типы |
| UI по макетам (MUI, состояния, адаптив) | 2.1, 2.2, 2.4, 2.5, 5.5, 9.2-форма | **0.4–0.5** | Макет + тема на входе, результат детерминирован |
| Auth, гарды, BFF | 1.1, 1.2, 1.3, 2.6 | **0.5–0.6** | Генерируется легко, но требует ручной security-проверки |
| Доменная логика, транзакции, гонки | 5.1, 5.3, 5.6, 9.2 | **0.6–0.7** | Модель предлагает решение, верификация — тестами вручную |
| События, outbox, уведомления | 3.5, 4.6, 6.1–6.3 | **0.5–0.6** | Схемы из contracts помогают, но идемпотентность проверяется на стенде |
| CQRS, SQL, оптимизация | 7.1–7.5 | **0.55–0.65** | `EXPLAIN` и данные на реальных объёмах — руками |
| Инфраструктура, эксплуатация, нагрузка | 0.3–0.5, 8.1–8.5 | **0.7–0.85** | Прогон стенда, бэкапы, нагрузочный тест — физически ручные |
| Документация, тесты, этапный аудит | R.1–R.6, docs, тесты | **0.6–0.7** | ИИ быстро находит дубли/дыры, но решение и верификация — за человеком |

Средневзвешенный по проекту коэффициент ≈ **0.55** (без буфера на проверку).

### 4.3 Сколько стоит «работать с нейросетью»

Чистое время генерации — не тот показатель, который нужно планировать. К оценке добавляется:

| Статья | Надбавка |
|---|---|
| Формулирование контекста (спека + макет + контракт + AC в промпт) | +10–15 % к времени задачи |
| Ревью сгенерированного кода, отсев лишнего и «умных» абстракций | +10–15 % |
| Правка галлюцинаций (несуществующие API/пути/типы) | +5–10 % |
| **Итого буфер проверки** | **×1.3** (заложен в сценарий C) |

Поэтому сценарий C = `задачи × коэффициент §4.2 × 1.3` + `аудиты × 0.7` + `пост-MVP × 0.6 × 1.3`.

**Что нейросеть не ускоряет** (оставляем плановые сроки): интеграционные прогоны в compose, отладку в окружении, нагрузочные тесты, бэкапы и восстановление, согласования и ворота Эпика R.

### 4.4 Риски ИИ-разработки и защита

| Риск | Влияние | Митигация (уже в процессе) |
|---|---|---|
| Галлюцинации API/путей контрактов | Баги, дрейф контрактов | Генерация только из `packages/contracts`; `tsc --noEmit`, CI на совместимость контрактов |
| Обход quality gate «быстрого фикса» | Техдолг растёт | CI-гейт (линт/типы/тесты) блокирует мердж; [Эпик R](functional-spec.md#эпик-r--этапный-аудит-поиск-проблем-рефакторинг-и-оптимизация) на выходе этапа |
| Нарушения границ FSD, раздутые слои | Связность | `eslint-plugin-boundaries`, чек-лист [fsd §9](fsd.md#9-чек-лист-ревью) |
| Ошибки доступа (BFF, presigned, роли) | Утечка медданных | Тесты 4.5/9.3 на каждый ownerType/роль, ревью человеком — генерация здесь не принимается на веру |
| «Скорость генерации» ≠ скорость сдачи | Срыв сроков | Планирование по AC и воротам этапа, а не по объёму строк |
| Нет промптов вне Этапа 1 | Потеря выигрыша | Дописать промпты для Этапов 2–5 по образцу `prompts-stage1.md` |

| Срок, остаток | ≈ 12 нед | ≈ 17–18 нед | ≈ 10 нед | 24 нед |
| Доля ИИ в подходе | 0 % | 0 % | системная (промпты, генерация, ревью) | — |
| Для чего пригоден | оценка «в идеале» | **базовый план и обещание сроков** | ускорение при том же процессе | верхняя граница коридора |

**Рекомендация:** внешние сроки планировать по **D (roadmap)**, внутренние задачи и загрузку команды — по **B**, выигрыш от нейросети (**C**) считать бонусом, который идёт в буфер на непредвиденное, а не в сокращение календаря вдвое. Разрыв B → C (~30 %) — реалистичный ориентир при системной работе, разрыв A → C (~45 %) — только при отсутствии интеграционных проблем.

## 6. Формулы пересчёта

```text
Чел-дни задачи:        S = 1, M = 3, L = 5
Чел-дни этапа:         Σ задач этапа + 14 (аудит R: M×4 + S×2)
Подэтап (2.1):         Σ задач + 3 (сокращённый аудит R.1/R.5/R.6)
Срок этапа, недели:    max( Σ этапа / 25 , критический путь этапа / 5 )
Срок проекта, недели:  Σ сроков этапов (ворота последовательны) × 1.1 (координация)

Сценарий B:            задачи × 1.5, аудиты × 1.0
Сценарий C:            задачи × коэффициент §4.2 × 1.3, аудиты × 0.7, пост-MVP × 0.6 × 1.3
Команда не 5 человек:  пересчитать Σ / (N × 5) и перепроверить критический путь
```

## 7. Допущения

1. Оценки спеки (`S/M/L`) — человеко-дни разработчика, без времени на обучение стеку (NestJS/Prisma/Keycloak команда осваивает в Этапе 0–1, это входит в буфер B).
2. Загрузка 100 % в расчётах A/B/C; отпуска, болезни, встречи не моделируются — покрываются буфером B (×1.5) и коэффициентом координации ×1.1.
3. Этапы идут последовательно (ворота Эпика R), внутри этапа — максимальный параллелизм.
4. Аудит Эпика R оценён как `M×4 + S×2 = 14` чел-дней на проход и выполняется после **каждого** этапа 0–5; подэтап 2.1 — сокращённый проход R.1/R.5/R.6 = 3 чел-дня (полный — на Этапе 3).
5. Сценарий C предполагает, что промпты есть (сейчас — только на Этап 1) и что генерация идёт под AC задачи, а не «в пустоту».
6. Стоимость инструментов ИИ (подписки) в трудозатраты не входит — считается отдельно как операционные расходы.
