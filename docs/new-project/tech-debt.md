## A. Идентичность и доступ (Эпик 1, 9.1)

**TD-01 · 1.6 · Управление пользователями и ролями — P1 (Бэклог)**
Не сделано ничего из пункта: нет страницы `/admin/users` (в `apps/web/src/app/(admin)/admin/` только `doctors`,
`patients`, `reports`, `schedule`, `specializations`), нет слайса `features/change-user-role` в `services/identity` (там
`register`, `register-doctor`, `health`), в `services/gateway/src/entities/authorization/route-policy.ts` нет
users-маршрутов, `user.role-changed.v1` только объявлен (`packages/contracts/src/events/index.ts`), защиты «последнего
админа» нет. _Следствие:_ не работает и пункт 9.1 «смена роли врача → событие», связка `user ↔ doctor` живёт только в
`catalog.doctor.userId`. _Шаг закрытия:_ admin-API Keycloak в identity + слайс + страница + публикация события + guard
«последнего админа»; перенос из бэклога в ближайший этап.

**TD-02 · 9.1 · Gateway не фильтрует маршрут врача — P1 (Найдено)**
`findPolicy` выбирает политику по самому длинному совпадающему префиксу, а для scheduling задан только общий
`{ path: '/api/scheduling', roles: [ADMIN, USER, DOCTOR] }`; правила с `/appointments/doctor` нет → `USER` проходит
шлюз, а 403 отдаёт лишь `scheduling`. _Следствие:_ AC9.1 «403 и на gateway, и на сервисе (защита в глубину)» выполнено
наполовину. _Шаг закрытия:_ добавить в `route-policy` специфичное правило
`GET /api/scheduling/appointments/doctor/** → [DOCTOR, ADMIN]` + тест в `services/gateway/test/route-policy.test.ts`.

**TD-03 · 1.1 · Нет e2e входа по ролям — P1 (Найдено)**
В `scripts/` только API-скрипты (`e2e-stage2`, `e2e-epic9`, `e2e-booking-race`, password-grant); playwright/cypress в
репо нет (`*.spec.ts`, `playwright.config.*` — 0 файлов). _Следствие:_ AC1.1 «вход → страница своей роли → выход →
редирект» не подтверждается автоматически. _Шаг закрытия:_ минимальный браузерный e2e на 3 роли (вход/выход/редирект) +
подключение к CI (см. TD-36).

**TD-04 · 1.1 · Нет редиректа для роли USER — P2 (Найдено)**
`homeRedirectFor` (`apps/web/src/shared/lib/route-guard.ts`) возвращает `/admin/doctors` для `ADMIN`, `/doctor/schedule`
для `DOCTOR` и `null` для `USER`; ТЗ требует `USER → /cabinet/profile` (в Этапе 1 — `/cabinet/record`). Расхождение
закреплено тестом `apps/web/test/route-guard.test.ts` («пациент и гость остаются на главной»). _Шаг закрытия:_
**требуется решение лида** — либо вернуть редирект по ТЗ и обновить тест, либо зафиксировать отклонение в
functional-spec.

**TD-05 · 1.3 · Нет e2e гардов — P2 (Найдено)**
Есть только unit `apps/web/test/route-guard.test.ts`; AC «Тесты на каждый сценарий (unit middleware + e2e)» закрыт
наполовину. _Шаг:_ добавить e2e: `USER`→`/admin/doctors` = 403-страница, гость→`/auth/login?callbackUrl=`.

**TD-06 · 1.4 · Нет интеграционного теста обрыва саги — P1 (Найдено)**
Компенсация, идемпотентность и `EMAIL_EXISTS` покрыты unit'ом с in-memory-фейками
(`services/identity/test/register-saga.test.ts`), но сценарий «patient down → повтор → ровно один пользователь и одна
карточка» в compose не выполняется нигде. _Следствие:_ пункт рисков roadmap («Саги и компенсации содержат баги») не
имеет защиты. _Шаг:_ e2e-сценарий в `scripts/` с остановленным `patient` (docker compose stop) + повторная регистрация.

**TD-07 · 1.5 · Шаблон письма не кастомизирован — P2 (Найдено)**
`infra/keycloak/realm-medical-portal.json` → `"emailTheme": "keycloak"` (штатный шаблон), требование чек-листа
«кастомизация письма (шаблон, язык) в манифесте» не выполнено. _Шаг:_ либо email-тема Keycloakify
(`initialize-email-theme`) с фирменным шаблоном, либо явно зафиксировать отказ в spec. **Закрывается
задачей [2.7](functional-spec.md#27-переделка-ui-для-keycloak-тема-и-письма--l)** (эпик 2, входит в Этап 2):
email-шаблоны темы `mp-portal` + `emailTheme` в манифесте.

**TD-08 · 1.5 · Logout всех сессий после сброса — P1 (Найдено)**
Ни конфигурации, ни кода, ни теста: grep `revoke|logout-all|invalidate` по репо даёт только `URL.revokeObjectURL`.
_Следствие:_ AC1.5 «Старые сессии невалидны после смены» не подтверждён (Keycloak по умолчанию не разрывает активные
сессии). _Шаг:_ required-action/reset-flow с завершением сессий (или `logout-all` после успеха) + проверка
`GET /userinfo` старым токеном.

**TD-09 · 1.5 · Нет e2e восстановления пароля — P2 (Найдено)**
Mailpit поднят (`infra/docker-compose.yml`), но цикл «запрос → письмо → смена → вход новым паролем» автоматически не
проверяется. _Шаг:_ сценарий в `scripts/` через Mailpit API (GET /api/v1/messages) → смена → вход password-grant.

**TD-10 · 9.1 · Нет приглашения врача по email — P2 (Найдено)**
grep `invite|executeActions` по репо — 0 совпадений; чек-лист 9.1 требует «приглашение по email … пароль задаёт
приглашённый». _Шаг:_ `Admin API executeActionsEmail` + шаблон письма (зависит от TD-07). **Закрывается
задачей [10.2](functional-spec.md#102-email-врача-и-приглашение-по-ссылке--l) подэтапа «Этап 2.1»** (там же: поле email
в форме 3.2, `email`/`userId` в модели, отказ от «простого кейса»).

## B. Веб и UI (Эпик 2)

**TD-11 · 2.6 · Нет инвалидации серверного кэша — P1 (Найдено)**
В `apps/web` отсутствуют `revalidateTag`, `revalidatePath`, `unstable_cache` (grep = 0) и упоминания
`doctor.updated.v1` / `specialization.changed.v1`. _Следствие:_ AC2.6/чек-лист «серверный кэш справочников + инвалидация
по событиям» не выполнены — устаревшие врачи/специализации до пересборки. _Шаг:_ `unstable_cache` + `revalidateTag` в
BFF-роутах/серверных компонентах, тег по событию (валидация через `router.refresh` или webhook-хук BFF).

**TD-12 · 2.6 · BFF без агрегации — P2 (Найдено)**
`apps/web/src/app/api/bff/[...path]/route.ts` — тонкий прокси; AC «один BFF-запрос страницы „Список врачей“ заменяет ≥ 2
вызовов gateway» кодом не подтверждается. _Шаг:_ агрегирующие BFF-эндпоинты для списков (врачи + специализации) либо
корректировка AC.
