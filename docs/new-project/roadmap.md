# План внедрения (вариант C)

Дорожная карта для выбранной архитектуры: микросервисы на **NestJS**, события через **RabbitMQ**, CQRS-отчёты, **FSD** во всех проектах ([architecture.md](architecture.md), [fsd.md](fsd.md)).

Длительность — для команды 3–5 разработчиков; привязка к датам — после оценки бэклога из [functional-spec.md](functional-spec.md). Численный расчёт трудозатрат (чел-дни, критический путь, календарь на команду 5 человек и сценарии с нейросетью) — в [estimates.md](estimates.md).

Ключевой принцип: **целевая архитектура C строится сразу, но доставляется поэтапно** — контракты, сервисы и outbox есть с начала, тяжёлые элементы (уведомления, CQRS, аудит) включаются по мере готовности.

## Этапный аудит — ворота каждого этапа

После **каждого** этапа (0–5) выполняется обязательный **[Эпик R — Этапный аудит](functional-spec.md#эпик-r--этапный-аудит-поиск-проблем-рефакторинг-и-оптимизация)** из functional-spec:

- **R.1** аудит на SOLID/KISS/DRY ([fsd.md §7](fsd.md#7-принципы-кода-solid-kiss-dry)) + метрики линта/покрытия/ревью до/после;
- **R.2** разбор логов/DLQ/TODO, баги → с фиксом и регресс-тестом;
- **R.3** рефакторинг (дубли, feature-envy, длинные функции) без изменения поведения;
- **R.4** оптимизация (N+1, индексы, бандл, лаг событий) с цифрами «до/после»;
- **R.5** архитектурная сверка (границы FSD, владение данными, контракты);
- **R.6** закрытие этапа: обновление `docs/`, метрики, задачи в бэклог, решение лида.

**Этап не закрыт, пока аудит не пройден.** Найденное вне объёма этапа уходит в бэклог следующего этапа, а не копится «на потом». Бюджет аудита — **~1 неделя на этап**, она входит в указанные ниже диапазоны недель; если аудит не укладывается — этап продлевается, но без зелёного аудита не закрывается.

**Подэтапы** (сейчас — [Этап 2.1](#этап-21--новые-требования-недели-1718)) закрываются **сокращённым проходом**: R.1, R.5, R.6 по задачам подэтапа (~3 чел-дни); полный R.1–R.6 выполняется на ближайшем этапе.

## Этапы

### Этап 0 — Платформа и контракты (недели 1–3)
Цель: `git clone` → `docker compose up` → каркас всех сервисов + зелёный CI.

- 0.1 монорепо + **ESLint-границы FSD** (`packages/eslint-config-fsd`), Prettier, tsconfig-пресеты;
- 0.2 качество кода в CI: линт/типы/формат/тесты как ворота (SonarQube исключён из стека);
- 0.3 compose: postgres, minio, keycloak, rabbitmq, nginx, mailpit (тома, healthcheck'и);
- 0.4 Keycloak-реалм из манифеста (роли, web-клиент, service-accounts);
- 0.5 MinIO-бакеты + presigned-клиент;
- 0.6 `packages/contracts`: OpenAPI + Zod-схемы событий + codegen;
- 0.7 каркас 8 сервисов по FSD + **MVC/Hexagonal** (порт в `entities`, адаптер в `shared/api`) + `/healthz`, `/readyz`;
- 0.8 Prisma per service + `migrate deploy` job + seed;
- 0.9 шаблон outbox/inbox;
- 0.10 логирование: pino → Filebeat → Elasticsearch + Kibana (ILM-ретеншн).

**Веха M1:** пустое приложение входит через Keycloak, CI зелёный, структура слоёв проверяется линтом.
**Ворота этапа:** Эпик R (R.1–R.6).

- Эпик 5 (`scheduling-service`: слоты, атомарное бронирование, статусы);

Макеты страниц Этапа: [design/README.md](design/README.md) (оболочка, вход/регистрация, врачи, управление записями, история).

**Веха M2:** первый end-to-end сценарий записи работает в compose-окружении; двойное бронирование невозможно доказать тестом.
**Ворота этапа:** Эпик R (R.1–R.6) — отдельное внимание: дубли валидации слотов, связность `web` ↔ сервисы, тонкий BFF и сохранение SSR.

### Этап 2 — Персональные данные, файлы и кабинет врача (недели 11–16)

## Definition of Done

1. Линт (вкл. **границы FSD**), Prettier, `tsc --noEmit`, тесты с покрытием — зелёные.
2. Тесты: unit (домен/`entities`), интеграционный (API-слайс), для изменений событий — тест идемпотентности потребителя.
3. Контракт обновлён в `packages/contracts` (OpenAPI/Zod), типы перегенерированы; дрейф ломает CI.
4. Миграция Prisma приложена, обратно совместима (или есть rollback).
5. События — через outbox, схема версионирована, потребитель идемпотентен.
6. Изменение задокументировано в `docs/`.
7. Проверено в compose-окружении; секретов в репозитории нет.
8. **Принципы SOLID/KISS/DRY соблюдены** ([fsd.md §7](fsd.md#7-принципы-кода-solid-kiss-dry)): нет дублированных правил, преждевременных абстракций, handler'ов с несколькими обязанностями; дублирование < 3 %, complexity в норме.
9. **Этапный аудит (Эпик R) пройден** перед закрытием этапа — без зелёного аудита этап не закрывается.

## Риски и митигация

| Риск | Влияние | Митигация |
|---|---|---|
| Микросервисная сложность съедает MVP | Сроки | Этапы 0–2 без брокера-зависимости: обмен событиями включается на Этапе 3 |
| Сложность отладки распределённого запроса | Инциденты | `x-request-id` с Этапа 0, pino, метрики DLQ/лага до нагрузки |
| Саги и компенсации содержат баги | Данные | Идемпотентные повторы, интеграционные тесты отказов на шагах |
| Рассинхрон контрактов | Переделка | Один `packages/contracts`, codegen, CI на совместимость |
| Нарушения FSD при росте числа сервисов | Архитектура | Общий пресет `eslint-config-fsd`, gate в CI, чек-лист на ревью |
| Двойное бронирование | Дефолт | Уникальный индекс + тест 5.6 |
| Операционная нагрузка RabbitMQ | Простой | Мониторинг очередей, persistent queues, runbook replay |
| Ключи/секреты в репозитории | Инцидент | pre-commit сканер, Docker secrets, ротация |
| Размывание ответственности сервисов | Связность | Таблица владения данными в [architecture.md §5](architecture.md#5-владение-данными) — правки только на арх-ревью |
| BFF превращается во «второй монолит» | Связность, скорость релизов | BFF тонкий по определению (маршруты только агрегируют/маппят) — чек-лист [2.6](functional-spec.md#26-bff-слой-и-ssr--l) и сверка на Эпике R |
| Расширение прав доступа на врача (документы пациентов) | Утечка медданных | Связь «врач–пациент» проверяется в `file-service` через `scheduling` (защита в глубину), одна функция прав (DRY), тесты на каждый ownerType/роль + сверка на Эпике R |
| Накопление долга между этапами | Сложные релизы, рост стоимости изменений | Обязательный **Этапный аудит (Эпик R)** как ворота каждого этапа: поиск проблем, рефакторинг, оптимизация |
| Рост объёма логов в Elasticsearch | Диск, шум, снижение полезности поиска | ILM-политика (hot/warm/delete), ротация docker-логов (`json-file`, max-size/max-file), уровень INFO в проде, алерты на размер индексов; настройки — как код в `infra/` |
