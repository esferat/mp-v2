# Промпты для реализации Этапа 2.1

Готовые промпты для AI coding-агента (OpenCode, Cursor, Claude Code и т.п.): постановка и выполнение задач **[Этапа 2.1 «Новые требования»](roadmap.md#этап-21--новые-требования-недели-1718)** плана ([roadmap.md](roadmap.md)) — задачи [Эпика 10](functional-spec.md#эпик-10--новые-требования-подэтап-этап-21) (10.1–10.3).

Источник истины — [functional-spec.md](functional-spec.md): промпты — это сжатая выжимка чек-листов и AC задач; при расхождении верить спеке и править промпт.

> **Статус этапа:** по [roadmap → Статус](roadmap.md#статус-по-факту-кода-mp-v2) подэтап **не начат** — промпты ниже являются основным рабочим инструментом. Требования появились 09.11.2026 и оформлены отдельным подэтапом; существующие задачи (3.2, 5.4, 9.1) не переписываются — 10.x их расширяют.

## Как использовать

1. **P0 (контекст)** — вставляется один раз в начало сессии (или кладётся в `AGENTS.md`/`.cursorrules` репозитория). Если Этапы 0–2 не готовы — **стоп**: сначала [prompts-stage0.md](prompts-stage0.md), [prompts-stage1.md](prompts-stage1.md), [prompts-stage2.md](prompts-stage2.md).
2. Порядок промптов = порядок зависимостей из спеки (здесь задачи независимы, порядок — P10.1 → P10.2 → P10.3: от простого к доменному). Один промпт = одна задача = один PR/коммит.
3. После каждого промпта агент обязан: прогнать `pnpm lint`/`typecheck`/`test`/`format:check`, свериться с AC, обновить `docs/` при изменении поведения и выдать отчёт в формате из промпта.
4. **Не объединять задачи в один заход** — AC каждой должны быть проверяемы отдельно; подэтап закрывается сокращённым аудитом (P-R ниже).
5. Фронтенд — на компонентах **`mp-ui-kit`**: недостающие компоненты добавляются в библиотеку, а не дублируются в `web`.

```text
Ты работаешь в монорепозитории mp-v2 (Next.js + NestJS + TypeScript strict + Prisma,

(Эпик 10): личный профиль для любой учётки, email врача с активацией по ссылке,
перенос записи на приём.

Прежде чем писать код, прочитай:

   канон статусной машины (§1, включая перенос), задачи 3.2/5.4/9.1 — их 10.x расширяют.
2. docs/new-project/fsd.md — обязательный Feature-Sliced Design (§3 Next.js,
   §4 NestJS + §4.4 MVC/Hexagonal, §6 нарушения, §7 SOLID/KISS/DRY).
3. docs/new-project/architecture.md — §5 (владение данными), §6.1 (BFF), §6.4 (каталог
   событий: appointment.rescheduled.v1), §7.9 (сценарий переноса записи).
4. docs/new-project/design/profile.md, doctor-form.md, appointments.md — макеты задач.
5. docs/new-project/tech-debt.md — не повторяй известные расхождения.

Правила (нарушение = блокер на ревью):
- FSD: импорты «сверху вниз», один вход у слайса (index.ts), без кросс-импортов соседних
  слайсов — проверяется lint'ом (packages/eslint-config-fsd).
- MVC + Hexagonal: controller только адаптер, порты в entities/repository, реализации
  в shared/api, DI-сборка в app; ядро не импортирует Prisma/amqplib/транспорт.
- Браузер ходит ТОЛЬКО в BFF: route handlers app/api/bff/*; страницы — Server Components;
  токен сессии не покидает сервер web.
- UI — библиотека mp-ui-kit (компоненты Mp*): недостающий компонент добавляется в
  библиотеку (компонент + Storybook-история + тест), а не собирается заново в web;
  прямой импорт @mui/* вне shared/ui запрещён линтом.
- Контракты и схемы событий — только из packages/contracts; свои не изобретать.

сменой пароля при первом входе и записью риска в спеку.

Формат работы: одна задача = один PR; перед сдачей — pnpm lint, pnpm typecheck,

Отчёт по задаче: реализованные слайсы/файлы, результаты команд, соответствие AC
```

### Промпт 10.1 — Личный профиль для учётки любой роли

Задача: [10.1](functional-spec.md#101-личный-профиль-для-учётки-любой-роли--l) · оценка `L` · макет: [profile.md](design/profile.md)

```text
Задача 10.1 «Личный профиль для учётки любой роли» (docs/new-project/functional-spec.md).
Прочитай её чек-лист и AC полностью и реализуй — единая форма профиля для всех трёх
ролей: правка собственных данных на маршруте своей роли.

- Один общий слайс features/edit-profile + виджет widgets/profile-form (форма, валидация,
  состояния, тесты — общие, DRY); три страницы-обёртки в route groups: /cabinet/profile
  (USER, уже есть — расширить), /admin/profile (ADMIN, новый), /doctor/profile
  (DOCTOR, новый).
- Источники данных по ролям (макет profile.md, таблица «Разница по ролям»):
  USER → patient-service (GET/PUT /api/patient/:id, задача 4.2); DOCTOR → identity
  (email) + catalog (ФИО, специализация — read-only, правит админ); ADMIN → identity
  (новые self-service эндпоинты GET/PATCH /api/identity/me).
- Набор полей: пациент — ФИО, дата рождения, email; врач — email (ФИО/специализация —
  read-only); админ — ФИО, email. Пароль — отдельным действием «Сменить пароль» →
  flow Keycloak (1.5).
- Правка только своих данных: sub из токена ↔ сущность, чужой id → 403. Админская
  правка врачей/пациентов остаётся на существующих админ-страницах.
- Смена email → identity → Keycloak Admin API (формат + уникальность → ошибка на поле),
  изменение логируется; email не попадает в события (PII) и не денализуется.
- ФИО меняются через существующие события: patient.updated.v1 (денализация в scheduling,
  < 5 с) и doctor.updated.v1.
- Пункт меню «Профиль» в шапке (design/layout.md) ведёт на маршрут своей роли;
  компоненты — mp-ui-kit (MpTextField, MpButton, MpSnackbar, MpSkeleton).

Слой: app (страницы-обёртки) + features/edit-profile + widgets/profile-form + shared/api;
бизнес-логики в page.tsx нет (FSD §3).
Тесты: unit валидации формы; интеграционный «пользователь правит чужой id → 403»;
render-тест для трёх ролей.

AC (сверь по пунктам): «Профиль» из шапки открывает свой маршрут для ADMIN/USER/DOCTOR,
гость → редирект, прямой URL чужого профиля → 403-страница; правка своих данных
сохраняется и видна после F5, PUT/PATCH с чужим id → 403; смена email действует
на следующем входе, занятый email → 409 с указанием поля; ФИО пациента после правки
видны в списках scheduling < 5 с; форма и валидация — один слайс (линт FSD зелёный).
Не делай: смену роли (это 1.6), восстановление пароля целиком (это 1.5), правку
данных чужой сущности из профиля.
Отчёт: файлы, команды, результаты тестов, соответствие AC.
```

### Промпт 10.2 — Email врача и приглашение по ссылке

Задача: [10.2](functional-spec.md#102-email-врача-и-приглашение-по-ссылке--m) · оценка `M` · макет: [doctor-form.md](design/doctor-form.md)

```text
Задача 10.2 «Email врача и приглашение по ссылке» (docs/new-project/functional-spec.md).
Админ указывает email при создании врача; вход под учётной записью активируется по
ссылке из письма. «Простой кейс» (пароль при создании → письмо с креденшелами) ОТКЛОНЁН —
не реализуй его.

- web: поле email в форме врача + чекбокс «создать учётную запись» (макет
  doctor-form.md, блок «Основная информация»); Zod-валидация формата, уникальность →
  409 на поле.
- Контракт/модель: email и userId в Doctor (functional-spec §1), DTO create-doctor/
  update-doctor, миграция db_catalog; в payload doctor.*.v1 — userId (без email: PII).
- Сага (9.1, уже реализована): пользователь Keycloak с ролью DOCTOR → catalog.doctor.userId;
  компенсация и идемпотентность по email сохраняются.
- Активация по ссылке: Admin API executeActionsEmail (UPDATE_PASSWORD) → письмо со
  ссылкой установки пароля (mailpit в dev); тема/шаблон письма — TD-07 (см. tech-debt.md);
  повторная отправка приглашения админом (тот же вызов, идемпотентно) — кнопка
  «Отправить ещё раз» в карточке врача.
- Email занят существующим пользователем → 409 с подсказкой «пользователь уже есть —
  выдача роли, задача 1.6»; создание дубля учётной записи запрещено.

Слой: web (features/create-doctor, update-doctor) + services/catalog + services/identity;
пароль и токены не логируются (grep по логам e2e).
Тесты: идемпотентность повторного создания врача с тем же email; письмо дошло (API
mailpit); пароль и токен приглашения отсутствуют в логах и в ответах API.

AC (сверь по пунктам): форма — email + чекбокс → врач создан, doctor.userId заполнен,
на email пришло письмо со ссылкой установки пароля; по ссылке пароль установлен → вход
под email → /doctor/schedule (AC 9.1); grep по логам e2e — пароль и токен приглашения
не встречаются; повторное создание врача с тем же email → один пользователь Keycloak,
существующий пользователь → 409 без дублей; doctor.created/updated.v1 содержат userId
и не содержат email.
Не делай: простой кейс с паролем в письме; смену ролей существующего пользователя
(это 1.6).
Отчёт: файлы, команды, результаты тестов, соответствие AC.
```

### Промпт 10.3 — Перенос и изменение записи на приём

Задача: [10.3](functional-spec.md#103-перенос-и-изменение-записи-на-приём--l) · оценка `L` · макет: [appointments.md](design/appointments.md)

```text
Задача 10.3 «Перенос и изменение записи на приём» (docs/new-project/functional-spec.md).
Админ меняет врача и/или дату-время существующей записи; запись одна, история не
теряется. Сценарий — architecture §7.9.

- Статусная машина (канон §1): перенос допустим из SUBMITTED/APPROVED — статус не
  меняется, обновляются слот, врач и денализованные ФИО/специализация; из DECLINED/
  CANCELLED/COMPLETED → 409.
- Транзакция scheduling (по образцу 5.3): свободность нового слота обеспечивает
  UNIQUE (doctorId, localDate, start) → конфликт 409 SLOT_TAKEN; новая дата не в прошлом;
  врач активен и есть в копии расписания (5.1); UPDATE + строка outbox одним commit.
- Контракт: PUT /api/scheduling/appointments/:id/reschedule {doctorId?, localDate,
  start, reason?} → 400 (валидация Zod), 409 (конфликт слота/статуса), 200 +
  AppointmentResponseDTO.
- Событие appointment.rescheduled.v1: appointmentId, старый/новый слот, doctorId
  (был/стал), patientId, инициатор, причина (опц.); Zod в packages/contracts, строка
  в каталоге architecture §6.4; потребители — notification, audit; report НЕ подключается
  (счётчик посещений не меняется).
- Шаблон «запись перенесена» в 6.2 (Этап 3); до подключения notification событие никто
  не слушает — это допустимо.
- web: действие «Перенести» в таблице записей (макет appointments.md, Menu «⋯») →
  диалог выбора врача/даты/слота (переиспользовать компоненты 5.2/5.3) с подтверждением;
  409 → «слот занят, выберите соседний»; компоненты — mp-ui-kit (MpDialog, MpSelect,
  MpStatusBadge, MpSnackbar).
- Инициатор на MVP — только ADMIN: USER/DOCTOR → 403 и на gateway, и в сервисе;
  пациентский перенос — вне объёма.

Слой: scheduling (entities/appointment + features/reschedule-appointment) + gateway
(route-policy) + web (features/reschedule-appointment, widgets/appointments-table);
бизнес-логика — в домене, не в controller.
Тесты: unit-статусной машины (недопустимые переходы → 409); интеграционный «два переноса
на один слот → 1×200 + 1×409»; идемпотентность; сверка проекции «до/после переноса —
без изменений»; e2e «перенос → история показывает новое время».

AC (сверь по пунктам): перенос SUBMITTED/APPROVED на свободный слот → 200, в БД одна
запись, слот и врач обновлены, списки и история показывают новые данные без дублей;
конфликт слота → 409, в БД ничего не изменилось; перенос из DECLINED/CANCELLED/
COMPLETED → 409; appointment.rescheduled.v1 уходит через outbox, проекция отчёта не
изменилась (тест сверки с db_schedule); USER/DOCTOR получают 403 на админском переносе —
и на gateway, и в сервисе; история пациента отражает новое время/врача.
Не делай: новый статус в статусной машине (перенос — тот же статус); изменение правил
проекции отчёта (report не участвует).
Отчёт: файлы, команды, результаты тестов, соответствие AC.
```

## P-INT — Интеграция: критерий закрытия Этапа 2.1

```text
Финальная интеграция Этапа 2.1 (docs/new-project/roadmap.md, «Критерий закрытия»).
Прогони три сквозных сценария в compose-окружении:

1. Профиль своей роли: входы под ADMIN, USER и DOCTOR → «Профиль» из шапки открывает
   маршрут своей роли; правка ФИО/данных сохраняется, после F5 видна; чужой id → 403.
2. Врач активируется по ссылке: админ создаёт врача с email (чекбокс «создать учётную
   запись») → письмо в mailpit → переход по ссылке → установка пароля → вход под email →
   /doctor/schedule; повторное создание с тем же email → дубля нет; в логах нет пароля
   и токена приглашения.
3. Перенос записи: админ переносит запись на другой слот/врача → в БД одна запись
   с новым временем, история пациента показывает новое время без дублей; попытка
   переноса на занятый слот → 409, данные не изменились; событие
   appointment.rescheduled.v1 в outbox, проекция отчёта не менялась.

AC = критерий закрытия roadmap: AC 10.1–10.3 зелёные + e2e-сценарии выше. Если что-то
не проходит — чини по задачам, а не «локальными фиксами» мимо спеки.
Отчёт: протокол прогона сценариев (шаги, результаты), список расхождений с
документацией и как закрыт.
```

```text
Формат итогового отчёта: чек-лист R.1/R.5/R.6 с результатами по пунктам, найденное →
```

## Definition of Done (на каждую задачу)

1. Линт (вкл. границы FSD), Prettier, `tsc --noEmit`, тесты с покрытием — зелёные.
