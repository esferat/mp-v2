# Feature-Sliced Design — обязательные конвенции

**Scope:** все внутренние проекты репозитория `mp-v2` — `apps/web` (Next.js) и все `services/*` (NestJS, включая `gateway`), а также инструментальные пакеты. Нарушение границ — блокер на ревью и в CI.

## 1. Принципы

1. **Слойность** — код разложен по слоям; каждый слой знает только о слоях ниже себя.
2. **Слайсы (фичи)** — вертикальные модули, отвечающие за одну область («запись на приём», «врачи»). Внутри слайса — высокая связность, между слайсами — низкая.
3. **Публичный API** — у каждого слайса один вход: `index.ts`. Внутренние пути (`features/book-appointment/lib/utils`) недоступны снаружи.
4. **Однонаправленные импорты** — только «сверху вниз»: `app → processes → pages → widgets → features → entities → shared`. Кросс-импорты между слайсами одного уровня запрещены.
5. **Композиция, не наследование** — вышестоящий слой собирает нижележащие, переиспользуя их через публичный API.

## 2. Слои

| Слой | Назначение | Примеры |
|---|---|---|
| `app` | Точка входа, глобальная конфигурация, провайдеры | layout приложения, `main.ts`, глобальные guard/filter |
| `processes` (опц.) | Кросс-страничные/кросс-фичевые сценарии, оркестрация | многошаговая запись к врачу, saga регистрации |
| `pages` | Страницы UI (в бэкенде не используется — см. §4) | `/doctors`, `/schedule`, `/report` |
| `widgets` | Крупные блоки UI, композиции features | таблица записей с фильтрами, карточка врача |
| `features` | Пользовательские действия / use-cases | `book-appointment`, `approve-appointment`, `upload-document` |
| `entities` | Базовая предметная модель и её правила | `Appointment` со статусной машиной, `Doctor`, `Slot` |
| `shared` | Технический слой без домена | UI-кит (обёртки Material UI, тема), http-клиент, prisma, конфиг, утилиты |

Правило импортов (для всех проектов):

| Слой | Может импортировать |
|---|---|
| `app` | processes, pages, widgets, features, entities, shared |
| `processes` | features, entities, shared |
| `pages` | widgets, features, entities, shared |
| `widgets` | features, entities, shared |
| `features` | entities, shared |
| `entities` | shared |
| `shared` | только внутренние модули `shared` |

Запрещено: импорт «вверх», импорт соседнего слайса того же уровня, глубокий импорт в чужой слайс (минуя `index.ts`), циклические зависимости.

## 3. Применение в Next.js (`apps/web`)

```
apps/web/src/
├── app/                        # слой APP + PAGES (route segments Next.js)
│   ├── layout.tsx              # глобальный layout, providers, error.tsx
│   ├── api/bff/                # BFF: route handlers (агрегация gateway → view-модели), см. §3
│   ├── (public)/auth/login/page.tsx      # ← страница: только композиция
│   ├── (admin)/doctors/page.tsx
│   ├── (admin)/doctors/[id]/page.tsx
│   ├── (cabinet)/record/page.tsx
│   ├── (doctor)/schedule/page.tsx        # кабинет врача: приёмы + внесение результата (9.2)
│   └── (doctor)/patients/page.tsx        # пациенты врача и их документы (9.3)
├── processes/                  # кросс-страничные сценарии
│   └── booking-wizard/         # шаги «специализация → врач → слот → подтверждение»
├── widgets/                    # блоки страниц
│   ├── appointments-table/
│   ├── doctor-appointments-table/  # приёмы врача (кабинет /doctor/schedule)
│   ├── patient-documents/     # документы пациента: список, загрузка, скачивание
│   ├── doctors-table/
│   ├── doctor-card/
│   └── layout/                 # header, sidebar, page-title
├── features/                   # действия пользователя
│   ├── book-appointment/
│   ├── approve-appointment/
│   ├── enter-visit-result/     # внесение результата приёма (врач, 9.2)
│   ├── upload-patient-document/
│   ├── signin/
│   └── ...
├── entities/
│   ├── appointment/
│   ├── visit-result/           # заключение/рекомендации к записи
│   ├── doctor/
│   ├── patient/
│   ├── specialization/
│   └── ...
└── shared/
    ├── api/                    # единый fetch-инстанс, перехват токена, ретраи, генерация типов из контрактов
    ├── ui/                     # обёртки Material UI: кнопка, инпут, таблица, модалка, дейтпикер, аватар, спиннер (прямой импорт @mui/* снаружи запрещён)
    ├── lib/                    # хуки, форматтеры дат/ФИО
    └── config/                 # env, константы маршрутов
```

Особенности:
- `page.tsx` — тонкие: собирают `widgets`, вызывают `features`, не содержат бизнес-логики.
- **SSR по умолчанию:** страница — Server Component; данные для рендера запрашиваются на сервере через `shared/api` (внутренний вызов `gateway`), браузер получает готовый HTML. Клиентские (`'use client'`) — только интерактивные острова: формы, таблицы с фильтрами, мастер записи.
- **BFF:** route handlers `app/api/bff/**` — единственная API-поверхность для браузера. Тонкие: маппинг и агрегация вызовов `gateway`, проброс `traceId`; бизнес-логики и доступа к БД в них нет (это домен сервисов). Клиентский код ходит в `/api/bff/*`, напрямую в `gateway` — нет.
- Серверные компоненты ходят в API через `shared/api`; клиентские взаимодействия — в `features` (вызовы BFF через тот же `shared/api`).
- Типы из `packages/contracts` (сгенерированные из OpenAPI/схем событий) импортируются только через `shared/api` или соответствующий `entities/*/model`.
- **Компоненты UI — библиотека [`mp-ui-kit`](../../packages/mp-ui-kit/README.md)** (компоненты `Mp*`): недостающий компонент добавляется в библиотеку (компонент + Storybook-история + тест), а не собирается заново в `web`; `shared/ui` — точка применения темы и прикладных обёрток над `Mp*`, прямой импорт `@mui/*` запрещён линтом (§6, №8).
- **Слои создаются по мере появления задач:** дерево выше — целевая структура; фактически в `apps/web/src` сейчас `app`, `features`, `widgets`, `shared` (+ служебные `src/types/*.d.ts`, например `next-auth.d.ts` — declaration-файлы, слоем FSD не считаются). `processes/` появляется с задачи [5.3](functional-spec.md#53-бронирование-записи--l) (`booking-wizard`), `entities/` — с первыми доменными моделями; отсутствие слоя ещё не нарушение, но и создавать «пустышки» под будущее не нужно (KISS).

## 4. Применение в NestJS (`services/*`, включая `gateway`)

Слой `pages` в бэкенде отсутствует: HTTP/gRPC-адаптеры живут внутри слайса фичи (см. §4.2).

### 4.1 Структура сервиса

```
services/scheduling/src/
├── app/                                # composition root
│   ├── main.ts
│   ├── app.module.ts                   # регистрирует слайсы (features/processes/entities/shared)
│   └── kernel/                         # глобальные guard/filter/interceptor: trace-id, ошибки, лог
├── processes/                          # кросс-фичевые сценарии (опц.)
│   └── appointment-lifecycle/          # согласование статусов + публикация событий
├── features/
│   ├── book-appointment/
│   │   ├── api/                        # controller + request/response DTO (адаптер входа)
│   │   ├── app/                        # use-case: handler команды
│   │   ├── model/                      # доменная логика слайса (валидация слота)
│   │   ├── lib/                        # приватные хелперы слайса
│   │   └── index.ts                    # public API слайса
│   ├── get-free-slots/
│   ├── approve-appointment/
│   ├── cancel-appointment/
│   └── get-appointments/               # query-side слайсы тоже здесь
├── entities/
│   ├── appointment/                    # модель + статусная машина (SUBMITTED→APPROVED/DECLINED, APPROVED→COMPLETED)
│   ├── slot/
│   ├── outbox/                         # модель записи outbox
│   └── repository/                     # интерфейсы репозиториев (портов) — доменные контракты
└── shared/
    ├── api/                            # PrismaClient, publisher брокера, Keycloak admin client
    ├── config/                         # схема env (Zod), константы
    ├── lib/                            # утилиты (id, время, ретраи)
    └── model/                          # общие константы: routing keys, статусы, ошибки
```

### 4.2 Правила для бэкенда

1. **Controller — адаптер фичи:** лежит в `features/<фича>/api/`, содержит только валидацию входа (DTO + pipe) и вызов use-case из того же слайса. Бизнес-логика в controller запрещена.
2. **Один Nest-модуль = один слайс:** `@Module` объявляется в `index.ts` слайса; `app/app.module.ts` лишь регистрирует их.
3. **`entities` не знает про Prisma/HTTP/брокер:** интерфейсы репозиториев объявлены в `entities/repository`, реализации — в `shared/api` (или `features/*/lib` для частных).
4. **Слайсы не импортируют друг друга.** Общее — только в `shared` или через публичный API процесса. Для кросс-фичевого сценария — слайс в `processes`.
5. **События:** константы routing keys и Zod-схемы полезной нагрузки — только из `packages/contracts` (через `shared/model`). Изобретение локальных схем запрещено.
6. **Prisma-схема сервиса** живёт в `services/<svc>/prisma/schema.prisma`; доступ к чужой БД невозможен ни на уровне Prisma, ни на уровне Postgres (отдельный пользователь БД на сервис).

### 4.3 Адаптация слоёв FSD к бэкенду

| Слой FSD | Бэкенд-эквивалент |
|---|---|
| `app` | `main.ts`, `AppModule`, глобальные guard/filter/interceptor |
| `processes` | оркестрация сценариев/саг между фичами |
| `pages` | — (нет UI); HTTP/gRPC-адаптеры → `features/*/api` |
| `widgets` | — (нет UI) |
| `features` | use-cases (команды и запросы) + их входные адаптеры |
| `entities` | доменные модели, правила (статусные машины), порты репозиториев |
| `shared` | Prisma, брокер, конфиг, утилиты, общие константы |

### 4.4 MVC + Hexagonal: соответствие слоям FSD

Внутренняя архитектура каждого сервиса — **MVC + Hexagonal** ([architecture.md §4.1](architecture.md#41-внутренняя-архитектура-сервиса-mvc--hexagonal)). Пересечение с FSD:

| Элемент MVC/Hexagonal | Слой FSD | Что здесь живёт |
|---|---|---|
| **Model** (домен + use-case) | `entities`, `features/*/app` | бизнес-логика, статусные машины, оркестрация одной операции |
| **View** (представление результата) | `features/*/api` (response-DTO, мапперы) | формат ответа, без ветвлений бизнеса |
| **Controller** (MVC-вход) | `features/*/api` | DTO + pipe-валидация, вызов use-case из того же слайса |
| **Порты** (interface) | `entities/repository`, `shared/model` | интерфейсы репозиториев, publisher/consumer, клиенсы внешних систем |
| **Адаптеры** (infrastructure) | `shared/api`, `features/*/lib` | Prisma-репозитории, RabbitMQ, Keycloak, SMTP |
| **Composition root** | `app` | DI-сборка: адаптеры подключаются к портам только здесь |

Правила:
1. Зависимости направлены внутрь: `shared/api` → порты, не наоборот; ядро не импортирует `@nestjs/*`-декораторы, кроме необходимых для DI-контейнера, и никак не импортирует `@prisma/client`/`amqplib` в `entities`.
2. Замена адаптера (Prisma → другой ORM, SMTP → другой провайдер) не трогает `entities` и `features/*/app` — это проверяется тестами ядра на in-memory-реализациях портов.
3. Нарушение «бизнес-логика в controller» (§6, №4) = нарушение и MVC, и Hexagonal одновременно.

## 5. Публичный API слайса

```ts
// features/book-appointment/index.ts  — ЕДИНСТВЕННЫЙ вход
export { BookAppointmentController } from './api/book-appointment.controller';
export { bookAppointment } from './app/book-appointment';
export type { BookAppointmentCommand } from './app/book-appointment';
```

- Экспорт только того, что нужно вышестоящим слоям.
- Глубокие импорты (`features/book-appointment/app/...`) ловятся линтом.
- Внутренние модули (`lib/`, `model/`) не экспортируются наружу вовсе.

## 6. Нарушения (типовые, блокирующие)

| # | Нарушение | Пример |
|---|---|---|
| 1 | Кросс-импорт фич | `features/approve-appointment` → `features/book-appointment/...` |
| 2 | Глубокий импорт в чужой слайс | `shared` → `features/book-appointment/app/handler` |
| 3 | Импорт «вверх» | `entities/appointment` → `features/...` |
| 4 | Бизнес-логика в controller/page | ветвление и работа с БД прямо в `api/*.controller.ts` |
| 5 | Доступ к чужой БД | `services/report` читает таблицы `db_schedule` напрямую |
| 6 | Локальная схема события | собственный интерфейс вместо Zod-схемы из `packages/contracts` |
| 7 | Отсутствие `index.ts` | импорт внутренностей слайса по длинному пути |
| 8 | Прямой импорт `@mui/*` вне `shared/ui` | `features/book-appointment` импортирует `@mui/material/Button` вместо обёртки из `shared/ui` |
| 9 | Бизнес-логика в BFF route handler | `app/api/bff/appointments/route.ts` валидирует слоты и пишет в БД вместо вызова use-case сервиса |
| 10 | Обход BFF: клиент идёт напрямую в `gateway` | `shared/api` в браузере вызывает `/api/scheduling/...` вместо `/api/bff/...` |

## 7. Принципы кода: SOLID, KISS, DRY

Обязательны во всех проектах репозитория. Проверяются на ревью и линтингом; нарушение — блокер до мержа. Практическая трактовка для нашего стека:

### SOLID
- **S — единственная ответственность:** один слайс = одна причина изменения; один handler/use-case = одна операция; controller — только адаптер (§4.2). *Нарушение:* handler, который валидирует, пишет в БД, публикует событие и форматирует ответ.
- **O — открытость/закрытость:** новые статусы/правила добавляются в статусную машину `entities/appointment`, а не правкой всех `switch`; новый потребитель событий — новая очередь и слайс, без изменения продьюсера.
- **L — подстановка:** реализации портов (репозитории, transport) взаимозаменяемы — in-memory-реализация в тестах не меняет контракт.
- **I — сегрегация интерфейсов:** тонкие порты (`IAppointmentRepository` не тащит методы отчёта), компоненты не получают пропсы, которые им не нужны.
- **D — инверсия зависимостей:** домен (`entities`) объявляет порты, инфраструктура (`shared/api`) реализует; сборка — в `app`.

### KISS
- Самое простое решение, пока не доказана необходимость сложности (кэш, абстракция, обобщение).
- Никаких слоёв/флагов/интерфейсов «на будущее» без второй реальной реализации.
- Ранний `return` вместо вложенных `else`; бизнес-логика — максимум 2 уровня вложенности.
- Сложность выносится в именованные функции с говорящими именами, а не в комментарии «здесь сложно».

### DRY
- Дублируется **знание**, а не строка: правило валидации, формула расчёта слота, маппинг статуса живут в одном месте (`entities`/`shared/model`) и переиспользуются через публичный API.
- Ложный DRY не допускается: код, использованный дважды и принадлежащий одному слайсу, остаётся в слайсе. Абстракция — на **третий** случай использования или при смене правила в двух местах.
- В `shared` выносится только то, что действительно общее для всех: контракты, константы событий, UI-примитивы, домен-нейтральные утилиты.

### Контроль
- Ревью (чек-лист §9) и **этапный аудит [Эпик R](functional-spec.md#эпик-r--этапный-аудит-поиск-проблем-рефакторинг-и-оптимизация)**: дублирование, циклы, complexity, глубина вложенности — на каждом этапе.
- ESLint: `complexity`, `max-depth`, `no-else-return`, `no-unused-vars` (усиливаются на этапном аудите).

## 8. Контроль соблюдения

1. **ESLint** — `eslint-plugin-boundaries` (или `no-restricted-imports` с path-паттернами) в общем пресете `packages/eslint-config-fsd`; подключается во все проекты без исключений.
   - элементы: `app`, `processes`, `pages`, `widgets`, `features`, `entities`, `shared`;
   - запрет глубоких импортов (`depth`), запрет кросс-слайсных зависимостей, запрет циклов.
2. **CI** — `pnpm lint` + `tsc --noEmit` + тесты; нарушение границ = красный билд.
3. **Ревью** — чек-лист §9; дубли/циклы/complexity ищутся здесь и на этапном аудите.
4. **Этапный аудит** — [Эпик R](functional-spec.md#эпик-r--этапный-аудит-поиск-проблем-рефакторинг-и-оптимизация) на выходе каждого этапа: сверка принципов §7, метрики до/после.

## 9. Чек-лист ревью

- [ ] Импорты соответствуют таблице §2 (нет «вверх», нет кросс-слайсных).
- [ ] У слайса есть `index.ts`, внешние импорты идут только через него.
- [ ] Controller/page не содержит бизнес-логики.
- [ ] Доменные правила живут в `entities`, не в `shared`.
- [ ] Схемы событий и типы API — из `packages/contracts`.
- [ ] Слайс имеет осмысленное имя в единственном числе (`book-appointment`, не `booking-utils`).
- [ ] Нет «служебных» слайсов-свалок (`shared/helpers/misc`).
- [ ] Принципы SOLID/KISS/DRY соблюдены (§7): нет дублированных правил, преждевременных абстракций, «умных» handler'ов с пятью обязанностями.
- [ ] BFF тонкий: route handler только агрегирует/маппит, бизнес-логика — в use-case сервисов; клиент не ходит в `gateway` напрямую.
- [ ] Зависимости направлены внутрь (§4.4): `entities`/`features/*/app` не импортируют `@prisma/client`, `amqplib`, транспортные модули NestJS.
