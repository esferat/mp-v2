# Промпты для реализации Этапа 0

Готовые промпты для AI coding-агента (OpenCode, Cursor, Claude Code и т.п.): постановка и выполнение задач
**[Этапа 0 «Платформа и контракты»](roadmap.md#этап-0--платформа-и-контракты-недели-13)** плана
([roadmap.md](roadmap.md)).

Источник истины — [functional-spec.md](functional-spec.md): промпты — это сжатая выжимка чек-листов и AC задач; при
расхождении верить спеке и править промпт.

> **Статус этапа:** по [roadmap → Статус](roadmap.md#статус-по-факту-кода-mp-v2) каркас Этапа 0 уже реализован
> (композиция, CI, контракты, сервисы, outbox, логи). Промпты пригодятся для сверки AC по пунктам, доработки незакрытого
> ([tech-debt.md](tech-debt.md): TD-16–TD-28) и для переиспользования подхода на других этапах/проектах.

## Как использовать

1. **P0 (контекст)** — вставляется один раз в начало сессии (или кладётся в `AGENTS.md`/`.cursorrules` репозитория).
   Этап 0 — старт с нуля, входных условий нет.
2. Дальше — строго **по порядку**: порядок промптов = порядок зависимостей из спеки. Один промпт = одна задача = один
   PR/коммит.
3. После каждого промпта агент обязан: прогнать `pnpm lint`/`typecheck`/`test`/`format:check`, свериться с AC, обновить
   `docs/` при изменении поведения и выдать отчёт в формате из промпта.
4. **Не объединять задачи в один заход** — AC каждой должны быть проверяемы отдельно, иначе не пройти этапный аудит
   (Эпик R).
5. Задача **0.2 не реализуется** (SonarQube исключён из стека) — промпт P0.2 только фиксирует решение и качество в CI.

## P0 — Контекст (один раз)

```text
Ты работаешь в монорепозитории mp-v2 (Next.js + NestJS + TypeScript strict + Prisma,
PostgreSQL, MinIO, Keycloak, RabbitMQ, nginx, Docker). Это Этап 0 — старт с нуля:
workspace чистый, нужно собрать платформу, контракты и каркасы сервисов.

Прежде чем писать код, прочитай:
1. docs/new-project/README.md — стек и состав монорепо.
2. docs/new-project/fsd.md — обязательный Feature-Sliced Design (§2 слои и импорты,
   §3 Next.js, §4 NestJS + §4.4 MVC/Hexagonal, §6 типовые нарушения, §7 SOLID/KISS/DRY).
3. docs/new-project/architecture.md — §2 (стек), §6.3 (события, outbox/inbox),
   §9 (инфраструктура, тома, healthcheck'и, наблюдаемость).
4. docs/new-project/functional-spec.md — Эпик 0: чек-листы и AC задач 0.1–0.10.
5. docs/new-project/roadmap.md — веха M1 и ворота этапа (Эпик R).

Правила (нарушение = блокер на ревью):
- FSD: импорты только «сверху вниз», один вход у слайса (index.ts), никаких кросс-импортов
  соседних слайсов — проверяется lint'ом (packages/eslint-config-fsd).
- Внутри сервисов — MVC + Hexagonal: controller только адаптер, порты в entities/repository,
  реализации в shared/api, DI-сборка в app; ядро не импортирует Prisma/amqplib/транспорт.
- UI-компоненты (для web) — библиотека mp-ui-kit (компоненты Mp*): недостающий компонент
  добавляется в библиотеку (компонент + Storybook + тест), а не собирается заново в web;
  прямой импорт @mui/* вне shared/ui запрещён линтом.
- Контракты (OpenAPI/Zod-типы) — только из packages/contracts; события — через outbox,
  схемы Zod версионируются; свои схемы не изобретать.
- Секреты/пароли/токены не логировать и не хранить в репозитории; в .env.example — только
  dev-значения.

Формат работы: одна задача = один PR; перед сдачей — pnpm lint, pnpm typecheck,
pnpm test, pnpm format:check.
Отчёт по задаче: реализованные файлы/слайсы, результаты команд, соответствие AC
(по пунктам), вопросы и риски. Если документация противоречит коду или задаче —
остановись и спроси, а не импровизируй.

Входные условия Этапа 0: чистый workspace, git-репозиторий (main + PR), доступный Docker.
Стартуй с 0.1 и дальше по порядку — каждый шаг зависит от предыдущих.
```

## Definition of Done (на каждую задачу)

Краткий чек-лист из [roadmap.md](roadmap.md#definition-of-done) — агент проверяет его перед сдачей каждого промпта:

1. Линт (вкл. границы FSD), Prettier, `tsc --noEmit`, тесты с покрытием — зелёные.
2. Тесты: unit (домен/`entities`), интеграционный (API-слайс); для событий — тест идемпотентности потребителя.
3. Контракт обновлён в `packages/contracts`, типы перегенерированы; дрейф ломает CI.
4. Миграция Prisma приложена, обратно совместима (или есть rollback).
5. События — через outbox, схема версионирована, потребитель идемпотентен.
6. Изменение задокументировано в `docs/`.
7. Проверено в compose-окружении; секретов в репозитории нет.
8. SOLID/KISS/DRY соблюдены ([fsd.md §7](fsd.md#7-принципы-кода-solid-kiss-dry)).
9. Этапный аудит (Эпик R) пройден перед закрытием этапа.
