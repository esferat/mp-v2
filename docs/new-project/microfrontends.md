# Микрофронтенды (MFE): анализ и границы выноса

**Статус:** анализ. На **MVP — одно приложение `web`** с границами FSD ([fsd.md](fsd.md)); MFE рассматриваются как
послеверсионный вариант роста. Документ фиксирует, *что* можно вынести, *в каком порядке* и *при каких предпосылках* —
чтобы решение принималось по критериям, а не по «хочется модно».

## 1. Текущая структура `web`

Одно Next.js-приложение, но уже разложенное на независимые зоны (route groups,
см. [fsd.md §3](fsd.md#3-применение-в-nextjs-appsweb)):

| Зона             | Маршруты     | Роль   | Состав                                         |
|------------------|--------------|--------|------------------------------------------------|
| Публичная / вход | `/auth/*`    | гость  | логин, регистрация                             |
| Админ-консоль    | `/admin/*`   | ADMIN  | врачи, расписание, записи, отчёты              |
| Кабинет пациента | `/cabinet/*` | USER   | профиль, запись (мастер), история              |
| Кабинет врача    | `/doctor/*`  | DOCTOR | приёмы, результаты приёма, документы пациентов |

Каждая зона изолирована слоями FSD: свои `widgets`, `features`, `entities` (слои создаются по мере роста — целевое
состояние, см. [fsd.md §3](fsd.md#3-применение-в-nextjs-appsweb)); пересечение — только `shared/*` (UI-кит, API-клиент,
константы), отдельные переиспользуемые `widgets` (например, `patients-table` — админка и кабинет врача) и `processes`
(мастер записи). **Это и есть границы будущих MFE:** общий `widgets`-файл при выносе становится пакетом или остаётся в
шелле.

## 2. Кандидаты на вынос (по убыванию выгоды)

| # | Часть                                          | Граница                      | Почему выносить                                                                                                                               | Когда выносить                                                                                    |
|---|------------------------------------------------|------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------|
| 1 | **Отчёты/аналитика** (`/admin/reports`)        | отдельный MFE внутри админки | Тяжёлые зависимости (графики, CSV-экспорт), медленный цикл релизов аналитики, пиковая нагрузка на чтение — изолируется без каскада на админку | Первый кандидат: как только отчёты начинают жить своим релизным циклом                            |
| 2 | **Админ-консоль** (`/admin/*`)                 | отдельное приложение         | Своя роль, своя аудитория (2–3 админа), независимые релизы справочников, можно деплоить/откатывать отдельно от кабинета                       | Появление второй команды или требование «админка падает — кабинет работает»                       |
| 3 | **Кабинет пациента** (`/cabinet/*`)            | отдельное приложение         | Основной трафик и пик записи; независимое масштабирование под нагрузку, отдельный UX-цикл                                                     | После админки, при росте трафика/нагрузочного инцидента                                           |
| 4 | **Кабинет врача** (`/doctor/*`)                | отдельное приложение         | Своя аудитория (врачи) и свой релизный цикл; ежедневный рабочий инструмент — падение портала не должно валить приёмы, и наоборот              | Вместе с выносом кабинета пациента или раньше, если появится отдельная команда врачебного контура |
| 5 | **Мастер записи** (`processes/booking-wizard`) | не MFE, а модуль             | Объём мал, связность со слотами/статусами высока; вынос оправдан лишь как отдельный «виджет-страница» внутри кабинета                         | Не выносить отдельно                                                                              |

**Не выносить в MFE никогда:**

- **вход/сессию** (Auth.js + Keycloak) — единая точка входа, общий шелл;
- **шелл** (layout, меню, roles-guard) — он и есть хост MFE;
- **`shared/ui` (тема MUI), `shared/api` (BFF-клиент), `packages/contracts`** — общий рантайм, публикуется как пакеты.

## 3. Что должно быть готово перед выносом (предпосылки)

1. **BFF** ([2.6](functional-spec.md#26-bff-слой-и-ssr--l)) — уже требование MVP: каждый MFE получает свой префикс
   `/api/bff/<mfe>/*`, иначе MFE начнёт дублировать вызовы gateway.
2. **SSR** — MFE обязаны рендериться на сервере (как и весь `web`); чистые CSR-MFE ломают требование «контент виден до
   гидрации».
3. **Единая сессия:** Keycloak-кука на общем домене + общий шелл проверяет сессию и роль до загрузки MFE.
4. **Общий рантайм как пакеты:** тема MUI (`shared/ui` → npm-пакет), API-клиент, типы `packages/contracts` — версии
   синхронизируются через CI монорепо.
5. **Границы FSD соблюдены** (линт зелёный) — если в одном приложении уже есть кросс-импорты зон, MFE их просто
   узаконит.

## 4. Варианты технологии

| Вариант                                                                                              | Плюсы                                                                                          | Минусы                                                                                                   | Вердикт                                                 |
|------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------|---------------------------------------------------------|
| **Отдельные Next.js-приложения за nginx** (path-routing: `/admin/*` → admin-app, `/cabinet/*` → web) | Просто, каждый MFE — обычный Next.js со своим SSR и BFF; независимый деплой без хрупкой сборки | Общий код — только пакетами (npm), нет общего рантайма «на лету»; нужен синхронизация версий пакетов     | **Рекомендуемый путь**                                  |
| **Module Federation** (Rspack/Webpack)                                                               | Общие модули подгружаются на лету, единый деплой                                               | Конфликт с App Router/RSC, хрупкая сборка, сложный локальный dev, отладка «какая версия MFE загрузилась» | Только если появится жёсткое требование общего рантайма |
| iframe                                                                                               | Полная изоляция                                                                                | Плохая SEO/SSR, проблемы с сессией и доступностью, двойной рендер                                        | Не подходит (SSR-требование)                            |

## 5. Порядок действий

1. **MVP:** одно приложение, границы FSD — ничего не выносить (KISS: стоимость MFE > выгоды при одной команде).
2. **Подготовка (уже в MVP):** зоны изолированы, `shared/*` не знает про зоны, BFF-префиксы не смешиваются — см.
   чек-лист [R.5](functional-spec.md#r5-архитектурная-сверка--s).
3. **Триггер к выносу:** вторая команда, независимый релизный цикл зоны или инцидент «падение зоны валит всё».
4. **Первый MFE:** отчёты → админка → кабинеты (пациента и врача) (таблица §2), каждый раз — отдельное решение на
   арх-ревью (Эпик R).

## 6. Риски MFE

| Риск                                            | Митигация                                                                                                                   |
|-------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------|
| Дрейф общих пакетов (тема, контракты) между MFE | Единый монорепо/CI, versions в пакетах, gate на совместимость                                                               |
| Дублирование BFF-логики в каждом MFE            | BFF тонкий по определению ([fsd.md §6, №9](fsd.md#6-нарушения-типовые-блокирующие)); агрегация — в общих серверных хелперах |
| Разъезд рантайма (React/MUI-версии)             | Общий `packages/*` с peerDependencies, CI на одновременную сборку                                                           |
| Сложность e2e через несколько приложений        | Один Playwright-проект с несколькими `baseURL`, контракты в `packages/contracts`                                            |
| Преждевременность (делаем «на будущее»)         | Триггер из §5 — без него MFE не начинаем (KISS)                                                                             |
