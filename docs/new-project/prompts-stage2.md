# Промпты для реализации Этапа 2

Готовые промпты для AI coding-агента (OpenCode, Cursor, Claude Code и т.п.): постановка и выполнение задач **[Этапа 2 «Персональные данные, файлы и кабинет врача»](roadmap.md#этап-2--персональные-данные-файлы-и-кабинет-врача-недели-1116)** плана ([roadmap.md](roadmap.md)).

Источник истины — [functional-spec.md](functional-spec.md): промпты — это сжатая выжимка чек-листов и AC задач; при расхождении верить спеке и править промпт.

> **Статус этапа:** по [roadmap → Статус](roadmap.md#статус-по-факту-кода-mp-v2) Этап 2 закрыт (аудит R зелёный), e2e `e2e-stage2`/`e2e-epic9` зелёные. Промпты пригодятся для сверки AC по пунктам, доработки незакрытого ([tech-debt.md](tech-debt.md): TD-29–TD-37) и для переиспользования подхода. Уточнения и новые требования к этому домену — в подэтапе [Этап 2.1](prompts-stage2-1.md) (Эпик 10).

## Как использовать

1. **P0 (контекст)** — вставляется один раз в начало сессии (или кладётся в `AGENTS.md`/`.cursorrules` репозитория). Если Этап 1 не готов — **стоп**: сначала задачи [prompts-stage1.md](prompts-stage1.md).
2. Дальше — строго **по порядку**: порядок промптов = порядок зависимостей из спеки. Один промпт = одна задача = один PR/коммит.
3. После каждого промпта агент обязан: прогнать `pnpm lint`/`typecheck`/`test`/`format:check`, свериться с AC, обновить `docs/` при изменении поведения и выдать отчёт в формате из промпта.
4. **Не объединять задачи в один заход** — AC каждой должны быть проверяемы отдельно, иначе не пройти этапный аудит (Эпик R).
5. Фронтенд — на компонентах **`mp-ui-kit`** (см. P0): недостающие компоненты добавляются в библиотеку, а не дублируются в `web`.

```text
Ты работаешь в монорепозитории mp-v2 (Next.js + NestJS + TypeScript strict + Prisma,

данные, файлы и кабинет врача (Эпики 4 и 9).

Прежде чем писать код, прочитай:

2. docs/new-project/fsd.md — обязательный Feature-Sliced Design (§2 слои и импорты,
   §3 Next.js, §4 NestJS + §4.4 MVC/Hexagonal, §6 типовые нарушения, §7 SOLID/KISS/DRY).
3. docs/new-project/architecture.md — §4.1 (MVC + Hexagonal), §5 (владение данными),
   §6.1 (BFF и SSR), §6.4 (каталог событий), §7.5–§7.8 (файлы, документы).
4. docs/new-project/functional-spec.md — задачи Этапа 2 с чек-листами и AC:
   Эпик 4 (4.1–4.6) и Эпик 9 (9.1–9.3); канон статусной машины — §1.
5. docs/new-project/design/*.md — макеты: doctor-patients.md, doctor-schedule.md,
   visit-result.md, history.md, profile.md.
6. docs/new-project/tech-debt.md — известные расхождения по Этапу 2, не повторяй их.

Правила (нарушение = блокер на ревью):
- FSD: импорты только «сверху вниз», один вход у слайса (index.ts), никаких кросс-импортов
  соседних слайсов — проверяется lint'ом (packages/eslint-config-fsd).
- Внутри сервисов — MVC + Hexagonal: controller только адаптер, порты в entities/repository,
  реализации в shared/api, DI-сборка в app; ядро не импортирует Prisma/amqplib/транспорт.
- Браузер ходит ТОЛЬКО в BFF: route handlers app/api/bff/*; страницы — Server Components
  (SSR по умолчанию); токен сессии не покидает сервер web.
- UI — библиотека mp-ui-kit (компоненты Mp*: MpTable, MpDialog, MpStatusBadge, MpEmptyState,
  MpAppShell и др.). Нужного компонента нет — добавь его в mp-ui-kit (компонент +
  Storybook-история + тест), а не собирай заново в web; прямой импорт @mui/* вне shared/ui
  запрещён линтом; дизайн-токены — только через тему.
- Контракты (OpenAPI/Zod-типы) — только из packages/contracts; события — через outbox,
  схемы Zod версионируются; свои схемы не изобретать.
- Секреты/пароли/токены не логировать и не хранить в репозитории; медицинские данные —
  права доступа проверяются на бэке (владелец/ADMIN/врач с приёмом), не в UI.

Формат работы: одна задача = один PR; перед сдачей — pnpm lint, pnpm typecheck,
pnpm test, pnpm format:check.
Отчёт по задаче: реализованные слайсы/файлы, результаты команд, соответствие AC
(по пунктам), вопросы и риски. Если документация противоречит коду или задаче —
остановись и спроси, а не импровизируй.

Проверь входные условия Этапа 2: docker compose up поднимает окружение, /healthz всех
сервисов 200, CI зелёный, Этап 1 закрыт (Auth.js, gateway, catalog, scheduling работают,
тест гонки бронирования зелёный). Если Этап 1 не выполнен — сообщи об этом и остановись.
```

```text

статус COMPLETED, событие доставлено, пациент видит результат в истории; параллельные/
повторные submit → ровно один результат; прямой API в обход формы → 409.
```

## Definition of Done (на каждую задачу)

Краткий чек-лист из [roadmap.md](roadmap.md#definition-of-done) — агент проверяет его перед сдачей каждого промпта:

1. Линт (вкл. границы FSD), Prettier, `tsc --noEmit`, тесты с покрытием — зелёные.
2. Тесты: unit (домен/`entities`), интеграционный (API-слайс); для событий — тест идемпотентности потребителя.
3. Контракт обновлён в `packages/contracts`, типы перегенерированы; дрейф ломает CI.
4. Миграция Prisma приложена, обратно совместима (или есть rollback).
5. События — через outbox, схема версионирована, потребитель идемпотентен.
6. Изменение задокументировано в `docs/`.
7. Проверено в compose-окружении; секретов в репозитории нет.
8. SOLID/KISS/DRY соблюдены ([fsd.md §7](fsd.md#7-принципы-кода-solid-kiss-dry)).
9. Этапный аудит (Эпик R) пройден перед закрытием этапа.
